HORIZON PORTAL · CREATOR PROGRAM

Build it. Validate it. Publish it.

The Creator Program is for developers who want their work to become part of the Horizon Workshop. The goal is not simply to upload a file. Every project needs clear information, a reproducible package, a version history and enough context for the community to understand what it is installing.

CREATOR PROTOCOL

What a Creator must do

Follow the same process for every submission. It keeps the Workshop understandable, makes moderation possible and prevents the public library from becoming a folder full of mystery ZIP files. Humanity has suffered enough from mystery ZIP files.

01

Request Creator access

Contact the Horizon team through Discord and explain who you are, what you create and what you intend to publish. Creator access is controlled and may require a Creator code or approval.

02

Prepare the project

Package the actual project cleanly. Do not submit an unfinished archive containing unrelated files, private data, credentials, executables or tools that are not required by the project.

03

Write complete metadata

Provide the project name, creator name, category, description, supported environment, required dependencies, version, installation instructions and known limitations. Add screenshots or media when they help explain the project.

04

Declare dependencies

Clearly state whether the project targets Dawn, SunRise or another supported environment. List required frameworks, companion mods, game versions and other dependencies so users can check compatibility before installation.

05

Submit for moderation

Publishing is not an instant public upload. The submission enters review so the team can check its structure, metadata, compatibility information and basic safety requirements before it becomes visible in Workshop.

06

Validation and safety checks

Content must be inspected for obvious malicious or unrelated payloads, suspicious files, credential harvesting, destructive behavior and misleading metadata. A project that cannot be safely understood or validated can be rejected or returned for correction.

07

Version everything

Every published update should have a clear version and changelog. Do not silently replace a release with a different build. Users need to know what changed and which version they are installing.

08

Keep the public project maintained

After publication, update compatibility information when the project changes. If a release becomes broken or unsafe, report it and provide a corrected version rather than leaving the community to discover the problem by accident.
